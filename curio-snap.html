    The product

    What Curio Snap brings together

    Curio Snap is designed for students aged 8–15 learning robotics through visual programming, simulation and connected devices. The brief describes both school and direct-learner use. The design file explores a Blockly workspace, generated Python, device connection, hardware configuration and AI training workflows. My freelance work focused on making this technical environment easier to navigate and understand.

    Problem framing

    The challenge

    A learner is asked to understand several things at once: which block to use, what the code means, how a device connects and whether the program or model worked. Exposing all technical detail at the same level can make the starting point unclear. The design challenge is to support a simple first action while keeping deeper tools available as the learner progresses.

    Users and scope

    Who it serves

    Students are the primary learner audience described in the brief. Schools are an intended institutional audience, and direct learners are also in scope. Teacher dashboards and parent tracking are described as future possibilities, so they are not presented here as completed features. The case study focuses on the workspace, device connection and guided AI-learning sequence.

    Task flow

    How the work moves

    Robotics path

    1. Open the workspace
    2. Find blocks or an example
    3. Build a program
    4. Inspect generated code and feedback
    5. Connect a device when needed
    6. Upload or run
    7. Observe the response

    AI path

    1. Choose a supported board
    2. Choose what to teach
    3. Add examples
    4. Train
    5. Test with new input
    6. Use the model in blocks or export to a device where supported

    Design decisions

    Key decisions

    1. The workspace separates making from inspecting.

    The toolbox, block canvas and code/output areas give learners recognizable places to find actions, assemble logic and inspect the result. Wireframes explore collapsed panels and alternative hardware-control placement, demonstrating attention to available working space.

    2. Device connection becomes an explicit choice.

    Bluetooth and USB connection options, connected states and upload screens expose the link between the digital workspace and physical hardware. Hardware dialogs also explore port selection and configuration rather than assuming the learner knows where each component is attached.

    3. AI training is organized as a sequence.

    The file includes board selection and training screens that move through input data, training and checking results. Learner-oriented language such as adding examples and testing the result helps make the sequence understandable without beginning with model architecture or deployment formats.

    4. Advanced tools remain available as the workflow expands.

    Code preview, terminal output, monitoring and model export provide depth for more involved tasks. Light and dark variants explore the same workspace in both themes.

    Design outcome and next validation

    What the design achieves, and how to test it

    The designs establish a connection between visual programming, hardware and AI experimentation. The next evaluation should test whether a learner can build a first program, recover from a connection failure and explain why an AI prediction may be uncertain. Useful measures include first-task completion, help requests, connection recovery and testing on examples not used during training. No learning improvement or accuracy gain is claimed here.

    Pausing to reflect

    Reflection

    An educational interface must help learners understand what they are doing as well as complete the action. The strongest direction in this work is a sequence that makes the relationship between examples, code, devices and feedback visible.
