    What GCC Safe Subway brings together

    Safe Subway is an operational interface for subway barrier management. Its designs include a location list, barrier-status information, selected-location controls, password recovery and a confirmation prompt. Some variants also expose water-level information. The case study centers on the sequence from identifying a location to deliberately requesting a change.

    The challenge

    An operational control must make both its target and its current state clear. With multiple subway locations in the same application, a user needs to know which location they are viewing before requesting an action. The design challenge is to keep location identity, barrier status and operation controls connected throughout the interaction.

    Who it serves

    The screens are intended for authorized operational staff rather than members of the public. The visible scope covers monitoring and initiating requests. A design screen does not establish the physical barrier’s response, interlocks or the system’s operational safety performance.

    How the work moves

    Operator

    1. Sign in
    2. Find a subway location
    3. Inspect current status
    4. Open the location control screen
    5. Choose an operation
    6. Review confirmation
    7. Send the request

    A complete implementation should then show a pending state and a device-confirmed result or failure. That final acknowledgement sequence is a recommendation for completion of the experience.

    Key decisions

    1. The location list supports recognition before action.

    Location names and status information allow operators to select the relevant subway before entering its controls. Search provides a direct route when the operator already knows the target location.

    2. The control screen keeps the selected location visible.

    This creates continuity between the list selection and the action. A confirmation prompt adds a deliberate checkpoint before a manual operation request is submitted.

    3. Screens and task flow are designed together.

    The file includes both UI screens and a task-flow diagram. Together they show how authentication, location selection and operation relate. Draft variants explore additional overview counts and operation history.

    What the design achieves, and how to test it

    The design establishes a clear location-to-operation sequence. The next evaluation should check whether operators can identify the intended subway, distinguish current status from an action, cancel an unintended request and recognize a failed or delayed response.

    Reflection
    For physical controls, clarity depends on more than a prominent button.

    The user must understand the target, the requested action and whether the device actually completed it.

    Decision 01 · Strategic

    Why I replaced the analytics dashboard with a focused subway list

    An operator opening the app during heavy rain needs one subway, fast, not a summary of all of them.

    Before the decision

    The draft home screen opened with page analytics: total subways (17), total barriers (44), open (37) and closed (3). The subway list sat below, with each row showing water level and barrier status.

    The turning point

    Option A · Draft

    Analytics first

    • Network-wide totals at a glance
    • The list starts below the fold
    • Two statuses per row to read
    Option B · Approved

    Search and list first

    • Search sits at the top
    • One barrier status and an update time per row
    • Totals and water level are no longer on screen

    Reasoning

    The core task is acting on one location. Putting search and the list first shortens the path to that task; totals are useful context but don't help pick a subway.

    Trade-off

    Operators lose the network overview and the water level that might explain why a barrier is closed. Both would need a home elsewhere.

    What I designed

    • Lo-fiAnalytics blocks, then the list
    • ApprovedSearch, then status and time per subway

    Result

    Live · impact not yet measured

    The home screen is a direct route to a subway. Whether operators find the intended location faster, and miss the totals, is still to be tested.

    • Information hierarchy
    • Recognition rather than recall
    • Aesthetic and minimalist design

    Decision 02 · Strategic

    Why the confirmation names the subway before a barrier moves

    Opening the wrong barrier isn't a typo you can undo. It changes traffic in a real subway.

    Before the decision

    In the draft detail screen, each barrier had its own Open or Closed button next to its status, with the location name at the top of the card.

    The turning point

    Option A · Conceptual

    One-tap toggle

    • Fastest in an emergency
    • A mis-tap moves a physical barrier
    • Nothing restates the target
    Option B · Approved

    Request, then a named confirmation

    • Location and current status above the buttons
    • The warning repeats the subway's name
    • One extra tap every time

    Reasoning

    A confirmation only prevents errors if it says what will happen. Naming the subway in the question turns "Are you sure?" into a check of the target.

    Trade-off

    An extra step when speed matters, and a pattern people can learn to tap through. The design still needs a pending and a device-confirmed state after "Yes".

    What I designed

    • DraftWarning over per-barrier controls
    • ApprovedTarget and status above the request
    • ConfirmationNames the subway, No or Yes

    Result

    Design outcome

    Every manual operation passes through a checkpoint that restates the target. The acknowledgement step (pending, done, failed) is designed as a recommendation, not yet as screens.

    • Error prevention
    • Visibility of system status
    • User control and freedom

    Decision 03 · Tactical

    Why control moved from individual barriers to the location

    Operators think in subways ("Rangarajapuram"), not in "Barrier 2, double lane".

    Before the decision

    The draft explored barrier lists (all, open, closed) with lane type, and a detail screen showing each barrier's status with an operation history: who opened it, manually or automatically, and when.

    The turning point

    Option A · Draft

    Manage each barrier

    • Fine control and a full history
    • More screens between list and action
    • Easy to act on the wrong barrier
    Option B · Approved

    One request per location

    • List → location → request
    • Matches how operators name places
    • No per-barrier control or history

    Reasoning

    Fewer, clearer targets reduce the chance of operating the wrong thing. The location is the unit operators recognise and talk about.

    Trade-off

    A double-lane subway with one barrier open and one closed can't be expressed, and the audit trail of who operated what is gone from the app.

    Result

    Design outcome

    The approved flow has three steps from list to request. Per-barrier states and operation history are open questions for a later version.

    • Match between system and real world
    • Error prevention
    • Hick's law

    Decision 04 · Tactical

    Why password recovery happens inside the app

    An operator locked out during a flood alert can't wait to find a reset link in their inbox.

    Before the decision

    The draft "Forgot password" screen asked for an email and had a single Send button, implying a reset sent elsewhere.

    The turning point

    Option A · Draft

    Send a reset by email

    • One field, one button
    • The user leaves the app
    • Depends on email access on the phone
    Option B · Approved

    Code and reset in the app

    • Email or SAP code, Generate, Verify
    • New password set on the next screen
    • Two screens and a code to handle

    Reasoning

    Keeping recovery in the app keeps the operator in one place. Accepting a SAP code as well as email fits staff who sign in with their employee code.

    Trade-off

    More steps than a link, and the code delivery channel still has to be reliable.

    What I designed

    • DraftEmail and Send
    • Approved · 1Generate a code, then verify
    • Approved · 2Set a new password

    Result

    Design outcome

    Recovery happens without leaving the app and accepts the identifier staff already use. Success rates haven't been measured.

    • Flexibility and efficiency of use
    • Help users recover from errors
