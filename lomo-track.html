    What LOMO Track brings together

    LOMO Track brings trip monitoring into a mobile workflow. The designs include an administrator’s trip list, an assigned-trip experience, trip details, location views, route exceptions and support tickets. The central design challenge was deciding what users need to understand immediately and what they can open when investigating a particular journey.

    The challenge

    A vehicle’s location is only one part of an operational decision. Users also need the trip’s source and destination, its current status and the events associated with it. On a small screen, these details compete for attention. The design addresses that complexity by separating the trip overview from deeper map and exception views while maintaining the vehicle and journey context.

    Who it serves

    The file distinguishes administrator and user authentication and shows both a multi-trip list and an assigned-trip home screen. The experience therefore supports two different starting points: finding a trip across a fleet and checking the trip relevant to an individual user. The case study focuses on these visible workflows rather than claiming a complete production permission model.

    How the work moves

    Administrator

    1. Sign in
    2. Search or filter trips
    3. Select a trip
    4. Review trip information
    5. Inspect the route
    6. Open an exception
    7. Return to the list

    Assigned-trip user

    1. Sign in
    2. Review assigned trip
    3. Open location or navigation
    4. Raise a ticket when help is needed
    5. Review ticket status

    Key decisions

    1. Trip context comes first.

    The trip summary groups vehicle identity, journey endpoints, status and distance before the user moves into detailed tracking. This gives the map a purpose: inspecting a journey the user already understands.

    2. Route views distinguish different parts of the journey.

    Forward, reverse and deviation labels give users a way to inspect route information in smaller groups. Event lists connect categories such as harsh braking, overspeed and halt with timestamps and a Map action, helping users move from a summary into a specific incident.

    3. Support stays connected to the trip.

    The ticket creation and created-ticket screens retain vehicle and route information alongside the issue type and status. The intended benefit is to reduce the amount of context a user must reconstruct when reporting a tracking issue.

    4. The design includes situations beyond an active trip.

    No-trip, loading, restricted-access and application-update screens make system state explicit. A playback screen adds Pause and Reset controls for reviewing recorded movement.

    What the design achieves, and how to test it

    The design provides distinct paths from trip overview to investigation and support. The next validation should test whether users can find a vehicle, explain an exception and raise a ticket without losing the original trip context. Useful measures are task completion, time to locate the relevant event and incorrect trip selections. These are proposed measures, not reported results.

    Reflection
    This project shows how information hierarchy can turn a dense tracking interface into a sequence of operational questions.

    A useful trip overview helps users decide what to inspect next, while the detailed views preserve the context needed to understand it.

    Decision 01 · Strategic

    Why I put trip context before the map

    A dot on a map doesn't say which trip it is, where it's going, or whether anything is wrong.

    Before the decision

    In the earlier Tanker Lorry Locking System, trip cards showed the invoice and vehicle numbers in small type next to a large "Map" button. Opening a trip went straight to a map with a single pin, followed by lock steps.

    The turning point

    Option A · Original app

    Map-first

    • The fastest route to a location
    • Trip identity and status are small or missing
    • The map has to explain everything on its own
    Option B · Chosen

    Context-first

    • Vehicle, status and endpoints come before the map
    • Each list card answers "which trip is this?"
    • One more tap to reach the map

    Reasoning

    A location only means something once you know which journey it belongs to. Showing the trip first gives the map a job: inspecting a journey the user already understands.

    Trade-off

    An extra step before the map. "View" on each card and a full-width "Locate on Map" button keep that step short.

    What I designed

    • Trip listVehicle, status, trip type, endpoints; search and status filters
    • Trip infoRoute, invoice, plant, start and ETA, then Locate on Map
    • Driver homeThe assigned trip, route and actual distance

    Result

    Live · impact not yet measured

    Every trip is identified by vehicle, status and route before any tracking. Time to find a vehicle and incorrect trip selections would show whether this works.

    • Information hierarchy
    • Recognition rather than recall
    • Progressive disclosure

    Decision 02 · Strategic

    Why I split the route into forward, reverse and deviation

    A tanker trip isn't one line on a map. It goes out, comes back, and sometimes leaves the planned route.

    Before the decision

    The earlier app's trip map showed one location pin. It had no route line and no driving events, so there was nothing to investigate.

    The turning point

    Option A · Conceptual

    Everything on one map

    • The complete picture at once
    • Outbound and return routes overlap
    • Event pins compete; hard to tie an event to a leg
    Option B · Chosen

    Route segments and an event sheet

    • Forward, Reverse and Route Deviation chips
    • Each event has a type, time and Map link
    • The combined picture needs a summary

    Reasoning

    Grouping events by leg lets someone answer "what happened on the way back?" without filtering a crowded map.

    Trade-off

    Segments hide the whole journey. A summary sheet lists all three with event counts (12 forward, 13 reverse, 9 deviation) so nothing is out of sight.

    What I designed

    • ForwardThe outbound leg and its events
    • ReverseThe return leg
    • Route deviationWhere it left the plan
    • SummaryAll three segments with counts
    • EventsType, time and a Map link to the spot

    My file holds more than a dozen Locate frames that explore route colours, pins and sheet states before this structure settled.

    Result

    Live · impact not yet measured

    Every driving event belongs to a leg of the journey and links to its place on the map. Time to locate the relevant event would show whether this helps.

    • Chunking
    • Progressive disclosure
    • Visibility of system status

    Decision 03 · Tactical

    Why support tickets carry the trip with them

    When tracking fails mid-trip, the person reporting it shouldn't have to retype the vehicle and route.

    Before the decision

    The earlier app ended the trip screen with a full-width "Create ticket" button and had a Tickets tab. The available screenshots don't show what the ticket form itself asked for.

    The turning point

    Option A · Conceptual

    A blank support form

    • Flexible for any problem
    • Vehicle and route typed again, with errors
    • Support has to work out which trip it is
    Option B · Chosen

    A ticket pre-filled from the trip

    • Vehicle number and route carried over
    • One question: "What's wrong?"
    • Issue categories need maintaining

    Reasoning

    The app already knows the trip. Asking for it again adds effort and mistakes at the worst moment.

    Trade-off

    A fixed list of issue types is quick but can't cover everything, so unusual problems need a fallback.

    What I designed

    • EmptyNo tickets yet, one clear action
    • CreateTrip details filled in, one question
    • CreatedStatus, ticket ID, issue and trip

    Result

    Design outcome

    Tickets keep the vehicle and route alongside the issue type and status. The intended benefit, less context to reconstruct, hasn't been measured.

    • Error prevention
    • Recognition rather than recall
    • Visibility of system status

    Decision 04 · Strategic

    Why one app serves transporters and drivers

    A transporter watching a fleet and a driver on one trip open the same app for very different reasons.

    Before the decision

    The earlier app's screens show one trip list as the home screen, with Home, Tickets and Profile tabs.

    The turning point

    Option A · Conceptual

    Two separate apps

    • Each tailored to one role
    • Two products to design, build and maintain
    • Patterns drift apart over time
    Option B · Chosen

    One structure, a home per role

    • Shared Home, Locate, Ticket and Profile
    • Admin home: trip list; driver home: assigned trip
    • Permissions must be explicit

    Reasoning

    Both roles care about the same objects: trips, locations and tickets. One structure keeps them speaking the same language; only the starting point changes.

    Trade-off

    Shared navigation means some areas matter less to drivers, and permission limits need their own screens (Unauthorized, Access Restricted).

    What I designed

    The file has an information architecture for each role. They contain the same structure: onboarding, authentication, and Dashboard, Locate, Tickets and Account under one navigation.

    Result

    Live · impact not yet measured

    Both roles share one navigation and vocabulary, and each starts where their work starts. Whether drivers find their trip without help is the next thing to test.

    • Consistency and standards
    • Flexibility and efficiency of use
    • Error prevention
