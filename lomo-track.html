    The product

    What LOMO Track brings together

    LOMO Track brings trip monitoring into a mobile workflow. The designs include an administrator’s trip list, an assigned-trip experience, trip details, location views, route exceptions and support tickets. The central design challenge was deciding what users need to understand immediately and what they can open when investigating a particular journey.

    Problem framing

    The challenge

    A vehicle’s location is only one part of an operational decision. Users also need the trip’s source and destination, its current status and the events associated with it. On a small screen, these details compete for attention. The design addresses that complexity by separating the trip overview from deeper map and exception views while maintaining the vehicle and journey context.

    Users and scope

    Who it serves

    The file distinguishes administrator and user authentication and shows both a multi-trip list and an assigned-trip home screen. The experience therefore supports two different starting points: finding a trip across a fleet and checking the trip relevant to an individual user. The case study focuses on these visible workflows rather than claiming a complete production permission model.

    Task flow

    How the work moves

    Administrator

    1. Sign in
    2. Search or filter trips
    3. Select a trip
    4. Review trip information
    5. Inspect the route
    6. Open an exception
    7. Return to the list

    Assigned-trip user

    1. Sign in
    2. Review assigned trip
    3. Open location or navigation
    4. Raise a ticket when help is needed
    5. Review ticket status

    Design decisions

    Key decisions

    1. Trip context comes first.

    The trip summary groups vehicle identity, journey endpoints, status and distance before the user moves into detailed tracking. This gives the map a purpose: inspecting a journey the user already understands.

    2. Route views distinguish different parts of the journey.

    Forward, reverse and deviation labels give users a way to inspect route information in smaller groups. Event lists connect categories such as harsh braking, overspeed and halt with timestamps and a Map action, helping users move from a summary into a specific incident.

    3. Support stays connected to the trip.

    The ticket creation and created-ticket screens retain vehicle and route information alongside the issue type and status. The intended benefit is to reduce the amount of context a user must reconstruct when reporting a tracking issue.

    4. The design includes situations beyond an active trip.

    No-trip, loading, restricted-access and application-update screens make system state explicit. A playback screen adds Pause and Reset controls for reviewing recorded movement.

    Design outcome and next validation

    What the design achieves, and how to test it

    The design provides distinct paths from trip overview to investigation and support. The next validation should test whether users can find a vehicle, explain an exception and raise a ticket without losing the original trip context. Useful measures are task completion, time to locate the relevant event and incorrect trip selections. These are proposed measures, not reported results.

    Pausing to reflect

    Reflection

    This project shows how information hierarchy can turn a dense tracking interface into a sequence of operational questions. A useful trip overview helps users decide what to inspect next, while the detailed views preserve the context needed to understand it.
